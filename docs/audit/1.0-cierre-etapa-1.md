  - `servicio-operaciones-partidos/`: Configuración Spring Boot 4.0.8 sobre Java 21, conexión a PostgreSQL (`esquema_operaciones`), endpoint diagnóstico `/health-check`, importación de `fulvo-common-lib`.
  - `api-gateway/`: Configuración reactiva Spring Cloud Gateway (`spring-cloud-starter-gateway-server-webflux:5.0.4`), Java 21 LTS, Spring Boot 4.0.8, Spring Cloud 2025.1.4, enrutamiento dinámico downstream con `RouteLocatorBuilder`, convertidor reactivo de roles `KeycloakReactiveRoleConverter`, `SecurityWebFilterChain` con Resource Server JWT de Keycloak y endpoint `/health-check`.

* **Endpoints y Contratos implementados y verificados:**
  - `GET http://localhost:8080/health-check`: Diagnóstico de salud perimetral (`200 OK`, `{"status":"UP"}`).
  - `GET http://localhost:8081/health-check`: Diagnóstico de salud de `servicio-torneos` (`200 OK`).
  - `GET http://localhost:8082/health-check`: Diagnóstico de salud de `servicio-operaciones-partidos` (`200 OK`).
  - `POST http://localhost:8090/realms/fulvo-realm/protocol/openid-connect/token`: Emisión de JWT por Keycloak con roles en el claim `realm_access.roles`.
  - Control de acceso perimetral en Gateway: peticiones sin token rechazan con `401 Unauthorized`; peticiones con token de rol insuficiente (ej. `ROL_FANATICO` hacia creación de torneos o sedes) rechazan con `403 Forbidden`.

* **Lógica técnica y de dominio aplicada:**
  - Aislamiento lógico de persistencia en PostgreSQL sin claves foráneas físicas cruzadas entre dominios (`torneo_id` y `arbitro_dni` desacoplados).
  - Inyección de dependencias estricta por constructor asistida por `@RequiredArgsConstructor` (sin `@Autowired` directo).
  - Propagación de trazabilidad distribuida extremo a extremo con cabecera `X-Correlation-ID` reflejada en los logs vía MDC `[%X{correlationId}]`.
  - Autenticación delegada a Keycloak e inspección criptográfica asimétrica de tokens JWT mediante claves públicas (`certs`), manteniendo la arquitectura 100% stateless.

#### 2. ¿Qué hubo que arreglar sobre la marcha?
* **Actualización del ecosistema Spring:** Se alinearon todos los microservicios y la librería común a Spring Boot 4.0.8, Spring Cloud 2025.1.4 y Lombok 1.18.38 con compatibilidad Java 21 LTS (`maven-compiler-plugin` 3.14.1 con `lombok-mapstruct-binding`), resolviendo inconsistencias de compilación entre starters de Gateway WebFlux y el parent de Boot.
* **Estandarización de `/health-check`:** Se desacopló la convención por defecto de Spring Boot Actuator (`/actuator/health`) mediante `management.endpoints.web.base-path: /` y `management.endpoints.web.path-mapping.health: health-check`, unificando las pruebas de infraestructura, monitores y Postman.
* **Resolución de roles Keycloak en WebFlux:** Se implementó `KeycloakReactiveRoleConverter` mapeando autoridades tanto en formato directo (`ROL_*`) como con el prefijo canónico de Spring Security (`ROLE_*`), garantizando compatibilidad con `hasAuthority` y `hasRole`.
* **Resolución de dependencias cruzadas de compilación:** Se incorporó `fulvo-common-lib` al `.m2` local previo a la compilación de los microservicios de negocio, garantizando builds reproducibles y limpios.

#### 3. ¿En qué difiere con lo establecido en el Plan Original?
* **Versiones de Framework:** Actualización de Spring Boot 3.3.4 a 4.0.8 y Spring Cloud 2023.0.x a 2025.1.4 para contar con el soporte más reciente del stack oficial y compatibilidad nativa con Java 21 LTS.
* **Endpoint de Salud:** Sustitución de `/actuator/health` por la URI semántica canónica `/health-check`.
* **Integración temprana de persistencia en operaciones:** Se incorporó el endpoint de lote de partidos (`POST /v1/partidos/lote`) y su colección de Postman como parte de la validación inicial de interconectividad.

#### 4. Puntos Clave para la Defensa Oral (Coloquio con Docentes)
* **Aislamiento de Persistencia:** Justificar por qué `esquema_torneos` y `esquema_operaciones` se modelan en esquemas independientes en la misma instancia de Postgres, garantizando desacoplamiento sin incurrir en costos de infraestructura duplicada.
* **Arquitectura Reactiva del Gateway:** Explicar el uso de Netty y Project Reactor en el API Gateway como único punto de ingreso perimetral de alto rendimiento sin bloqueo de hilos.
* **Trazabilidad Distribuida:** Demostrar cómo `CorrelationIdFilter` y el filtro global del Gateway garantizan que cualquier request mantiene un identificador unívoco a lo largo de todos los microservicios y logs de consola.
* **Seguridad OIDC y Stateless:** Destacar que los microservicios validan tokens JWT de forma asimétrica (JWK Set), sin necesidad de consultar a Keycloak en cada petición downstream.
