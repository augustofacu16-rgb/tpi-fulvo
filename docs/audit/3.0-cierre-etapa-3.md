#### 2. ¿Qué hubo que arreglar sobre la marcha?
* **Apertura de la Ruta de Cancelación en API Gateway:**
  - *Problema:* Al invocar `PATCH /v1/partidos/{id}/cancelacion` con token de `arbitro1`, el Gateway respondía `403 Forbidden` informando privilegios insuficientes.
  - *Causa:* En `SecurityConfig.java`, la autorización para `ROL_ARBITRO` contemplaba `/v1/partidos/*/estado` pero no `/v1/partidos/*/cancelacion`, cayendo en la regla comodín `PATCH /v1/**` reservada a `ROL_ORGANIZADOR`.
  - *Solución:* Se incorporó `"/v1/partidos/*/cancelacion", "/v1/partidos/*/cancelacion/**"` al conjunto de rutas permitidas para `ROL_ARBITRO`, recompilando exitosamente el microservicio Gateway.
* **Manejo de Coordenadas Duplicadas en Sedes (Postgres vs JPA):**
  - *Problema:* El intento de crear el índice `uq_sede_coordenadas` en PostgreSQL falló con error `23505 (Key is duplicated)` debido a registros preexistentes de pruebas, y el borrado directo fallaba por clave foránea `partido_sede_id_fkey`.
  - *Solución:* Se actualizaron las coordenadas de los registros secundarios para desagruparlos sin romper la integridad referencial de los partidos ya jugados, se aplicó la constraint `UNIQUE`, y se blindó la validación en Java mediante `existsByLatitudAndLongitud` en `SedeService` para responder `409 Conflict` antes de alcanzar el driver JDBC.
* **Diferenciación entre Reprogramación y Conflicto Horario:**
  - Al validar la ventana de $\pm 2$ horas, se verificó que el motor excluyera el propio `partidoId` evaluado; de este modo, reprogramar la fecha/hora de un partido existente no colisiona consigo mismo.
* **Consulta de Goleadores y Enlace de Datos Federados:**
  - El cómputo de goleadores en `TablaPosicionService` se ajustó para utilizar el método derivado de Spring Data JPA `findAllByTipoAndPartido_TorneoIdAndPartido_Estado(TipoActuacion.GOL, torneoId, EstadoPartido.FINALIZADO)` y consultar sincrónicamente a `servicio-torneos` (`/v1/torneos/{id}/jugadores-plantel`) empaquetando los datos en `JugadorPlantelDTO`.

#### 3. ¿En qué difiere con lo establecido en el Plan Original?
* **Implementación de Patrones de Diseño Canónicos (GoF):**
  - La lógica del aggregate `Partido` y `TablaPosicion` evolucionó hacia una arquitectura DDD orientada a dominio rico:
    - **Patrón State:** La máquina de estados de los partidos no es un simple switch en el servicio, sino clases de estado polimórficas (`EstadoDelPartido`) que encapsulan transiciones legales y prohíben manipulaciones externas de setters.
    - **Patrón Strategy:** La validación de formatos (Liga vs Llaves) para empates y desempate por penales se aisló en estrategias desacopladas (`EstrategiaLiga`, `EstrategiaLlaves`).
    - **Patrón Adapter:** La geocodificación externa se desacopló mediante puertos e interfaces (`GeocodificacionPort`).
* **Integración de Nombres y Apellidos en la Tabla de Goleadores:**
  - El diseño original sólo requería devolver ID de equipo, dorsal y cantidad de goles. Se potenció la experiencia integrando un DTO liviano en `fulvo-common-lib` para enriquecer la respuesta con el nombre y apellido del futbolista registrado en Torneos, manteniendo el desacoplamiento de persistencia.

#### 4. Puntos Clave para la Defensa Oral (Coloquio con Docentes)
* **Validación Criptográfica de Identidad Arbitral (Zero-Trust):**
  - Defender cómo se vincula la seguridad perimetral con la lógica de negocio: el API Gateway valida la firma del JWT y extrae los roles; downstream, `servicio-operaciones-partidos` extrae el claim estándar `sub` (UUID del usuario en Keycloak) y verifica que coincida con el `usuarioId` del colegiado asignado al partido. Nadie, ni siquiera un usuario con rol árbitro, puede iniciar o asentar actas de un partido ajeno.
* **Máquina de Estados y Dominio Rico (State & Strategy):**
  - Justificar la eliminación de setters anémicos en la entidad `Partido`. Las transiciones (`PROGRAMADO` $\to$ `EN_CURSO` $\to$ `FINALIZADO` / `CANCELADO`) son controladas por el patrón State, impidiendo incoherencias como asentar goles en partidos no iniciados o cancelar encuentros finalizados.
* **Regla Anti-Superposición Horaria (RN-05):**
  - Explicar la ventana de exclusión mutua de 2 horas previas y posteriores: un árbitro o un predio no pueden ser agendados para dos eventos deportivos si la diferencia temporal absoluta entre sus horarios de inicio es estrictamente menor a 120 minutos.
* **Control Estricto de Planteles y Sanciones Disciplinarias (RN-11):**
  - Demostrar el desacoplamiento de equipos y jugadores: el sistema controla rigurosamente el cupo máximo de 5 sustituciones de buena fe y bloquea de manera taxativa la sustitución de futbolistas inhabilitados disciplinariamente (`suspendido == true`).
* **Desacoplamiento Físico con Claves Lógicas:**
  - Resaltar ante los profesores que `servicio-operaciones-partidos` y `servicio-torneos` operan en esquemas relacionales independientes (`esquema_operaciones` y `esquema_torneos`) vinculados exclusivamente mediante identificadores numéricos lógicos (`torneoId`, `equipoId`), cumpliendo los estándares de microservicios sin claves foráneas físicas cruzadas.
