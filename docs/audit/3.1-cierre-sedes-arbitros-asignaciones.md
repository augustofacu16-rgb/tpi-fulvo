## 2. Decisiones técnicas

- Las relaciones internas de `Partido` con `Sede` y `Arbitro` se modelan mediante `@ManyToOne`.
- Las referencias a torneos y equipos continúan siendo identificadores lógicos, porque pertenecen a otros servicios.
- La asignación se ejecuta dentro de una transacción con bloqueos pesimistas (`@Lock(LockModeType.PESSIMISTIC_WRITE)`).
- Se implementó un orden determinístico de adquisición de bloqueos pesimistas (`Partido` -> `Sede` -> `Arbitro`) antes de evaluar conflictos, garantizando atomicidad en PostgreSQL y eliminando el riesgo de deadlocks entre transacciones concurrentes.
- Se excluye el partido que se está actualizando de las consultas de conflicto.
- Los límites de la ventana horaria son estrictos: una diferencia exactamente igual a dos horas se permite; una diferencia menor genera conflicto.
- La excepción `ConflictoHorarioException` extiende `ConflictoEstadoException`, por lo que se responde con `409 Conflict` mediante el manejador común.
- En `ArbitroService`, la persistencia se fuerza con flush inmediato dentro de un bloque protegido; colisiones de clave primaria / unicidad (SQLState 23505) se capturan y traducen a `ConflictoEstadoException` (HTTP 409), preservando excepciones no relacionadas sin convertirlas indiscriminadamente.
- `asignadoPartido` se mantiene como indicador auxiliar; la disponibilidad real se determina consultando los horarios existentes.
