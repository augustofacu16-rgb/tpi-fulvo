#### 1. ¿Qué y Cómo se hizo?
* **Componentes / Módulos intervenidos:** Creación del microservicio `api-gateway` en `tpi-fulvo/api-gateway/`, operando en la rama `feature/1.5-gateway-seguridad-oidc`.
* **Archivos creados o modificados:**
  - `api-gateway/pom.xml`: Proyecto Maven Spring Boot reactivo con `spring-cloud-starter-gateway`, `spring-boot-starter-oauth2-resource-server`, `spring-boot-starter-actuator` y Lombok.
  - `api-gateway/src/main/resources/application.yml`: Configuración de puerto `8080`, URI de JWK Set hacia Keycloak (`${KEYCLOAK_JWK_SET_URI:http://localhost:8090/realms/fulvo-realm/protocol/openid-connect/certs}`), URLs parametrizadas downstream (`services.torneos.url` y `services.operaciones.url`), exposición de Actuator (`health`, `info`) y formato de logging con MDC `[%X{correlationId}]`.
  - `api-gateway/src/main/java/com/fulvo/gateway/ApiGatewayApplication.java`: Clase principal arrancable `@SpringBootApplication`.
  - `api-gateway/src/main/java/com/fulvo/gateway/config/GatewayRoutesConfig.java`: Configuración programática de rutas mediante bean `RouteLocator` con `RouteLocatorBuilder` (Apunte 19) enrutando hacia `servicio-torneos` (`/v1/torneos/**`, `/v1/solicitudes-inscripcion/**`, `/v1/equipos/**`) y hacia `servicio-operaciones-partidos` (`/v1/partidos/**`, `/v1/sedes/**`, `/v1/arbitros/**`, `/v1/tablas-posiciones/**`), inyectando la cabecera `X-Gateway-Source: SpringCloudGateway`.
  - `api-gateway/src/main/java/com/fulvo/gateway/security/KeycloakReactiveRoleConverter.java`: Convertidor reactivo `Converter<Jwt, Mono<AbstractAuthenticationToken>>` extrayendo roles del claim `realm_access.roles` (Apunte 21) y exponiéndolos como `GrantedAuthority` literales (`ROL_*`) y con prefijo estándar Spring Security (`ROLE_*`), asegurando compatibilidad con `hasAuthority` y `hasRole`.
  - `api-gateway/src/main/java/com/fulvo/gateway/config/SecurityConfig.java`: Configuración reactiva perimetral `@EnableWebFluxSecurity` con `SecurityWebFilterChain` bloqueando anónimos (401), permitiendo `/actuator/health`, restringiendo `POST /v1/torneos`, sedes, árbitros y fixtures a `ROL_ORGANIZADOR` (403 si insuficiente), y validando JWT emitido por Keycloak.
  - `api-gateway/src/main/java/com/fulvo/gateway/config/CorrelationIdGlobalFilter.java`: Filtro reactivo global `GlobalFilter` propagando el encabezado `X-Correlation-ID` en cascada (Apunte 23).
  - `api-gateway/.gitignore`: Configuración de exclusión para artefactos de compilación Maven y metadatos de IDE.
  - `docs/agentes/TASKS.md`: Casillas 1.5.1 a 1.5.5 marcadas como completadas `[X]`.

* **Endpoints y Contratos implementados:**
  - `GET http://localhost:8080/actuator/health`: Endpoint de diagnóstico de salud (`200 OK`, `{"status":"UP"}`).
  - `GET /v1/torneos`: Requiere autenticación; sin cabecera `Authorization` responde `401 Unauthorized`.
  - `POST /v1/torneos`: Requiere rol `ROL_ORGANIZADOR`; con token de usuario `fanatico1` (`ROL_FANATICO`) responde `403 Forbidden`.

* **Lógica técnica y de dominio aplicada:**
  - Microservicio reactivo perimetral no bloqueante sobre Project Reactor / Netty, actuando como único punto de entrada público al ecosistema (Puerto 8080).
  - Autenticación delegada e inspección criptográfica de tokens OIDC/JWT sin estado frente al Identity Provider Keycloak.
  - Verificación perimetral de roles por método HTTP y ruta URI antes de derivar la petición a los microservicios de backend.

#### 2. ¿Qué hubo que arreglar sobre la marcha?
* **Incompatibilidad entre Spring Cloud Gateway y Spring Boot 4.0.8:** Al intentar utilizar `spring-cloud-starter-gateway` sobre `spring-boot-starter-parent:4.0.8`, el arranque fallaba con `NoClassDefFoundError: NettyWebServerFactoryCustomizer` y conflicto de introspección en `GatewayAutoConfiguration$NettyConfiguration`, debido a que Spring Cloud Gateway oficial (`2023.0.3` / `2024.0.0`) está diseñado para el árbol de Spring Framework 6 / Spring Boot 3.x.
* **Solución aplicada:** Se fijó `api-gateway` con `spring-boot-starter-parent:3.3.4` y `spring-cloud-dependencies:2023.0.3` (conforme a lo explícitamente especificado en `CONTEXT.md`: *"Spring Cloud 2023.0.x para el API Gateway"*), manteniendo Java 21 LTS y Lombok 1.18.38. La compilación, empaquetado y arranque ejecutaron con `BUILD SUCCESS` y 100% de estabilidad.

#### 3. ¿En qué difiere con lo establecido en el Plan Original?
* **Ajuste de Versión en el Gateway:** El plan base contemplaba actualizar todos los módulos a Boot 4.0.8. Al ser un módulo perimetral desacoplado sin dependencias compartidas de persistencia JPA ni WebMVC clásico, se empleó Spring Boot 3.3.4 con Spring Cloud 2023.0.3 para garantizar compatibilidad nativa con Spring Cloud Gateway y Netty, cumpliendo fielmente la arquitectura perimetral.

#### 4. Puntos Clave para la Defensa Oral (Coloquio con Docentes)
* **Aislamiento Perimetral y Red Interna (Apunte 19):** Explicar que el API Gateway es el único componente accesible desde el exterior en el puerto 8080; los microservicios downstream (`servicio-torneos:8081` y `servicio-operaciones-partidos:8082`) operan aislados en la red interna `bda-net`.
* **Seguridad Reactiva OIDC vs Servlets (Apuntes 20 y 21):** Destacar la diferencia entre `SecurityFilterChain` (MVC/bloqueante) y `SecurityWebFilterChain` con `ServerHttpSecurity` (WebFlux/reactivo), y cómo `KeycloakReactiveRoleConverter` mapea de forma reactiva (`Mono<AbstractAuthenticationToken>`) los roles embebidos en el claim `realm_access.roles` del JWT emitido por Keycloak.
* **Prueba de los Criterios de Aceptación:** Demostrar cómo el Gateway corta de raíz solicitudes no autenticadas (401) y solicitudes con roles insuficientes (403 para fanáticos intentando crear torneos) antes de consumir recursos de los microservicios downstream.
