* **Endpoints y Contratos implementados:**
  - `GET http://localhost:8080/swagger-ui.html`: Interfaz unificada de Swagger UI accesible públicamente desde el exterior, con selector desplegable entre servicios.
  - `GET http://localhost:8080/api/torneos/v3/api-docs`: Enrutado y reescrito hacia `http://localhost:8081/v3/api-docs` retornando la especificación OpenAPI 3.0 viva de `servicio-torneos`.
  - `GET http://localhost:8080/api/partidos/v3/api-docs`: Enrutado y reescrito hacia `http://localhost:8082/v3/api-docs` retornando la especificación OpenAPI 3.0 viva de `servicio-operaciones-partidos`.
  - Esquema de seguridad interactivo global `bearerAuth`: Botón "Authorize" en Swagger UI permitiendo ingresar tokens JWT de Keycloak para probar endpoints protegidos directamente desde el navegador.

* **Lógica técnica y de dominio aplicada:**
  - Agregación distribuida de documentación en arquitectura de microservicios: cada servicio genera su propia especificación OpenAPI viva basada en su código y controladores actuales, desacoplada físicamente.
  - El API Gateway actúa como agregador perimetral de documentación OpenAPI 3.0, centralizando en un único punto de entrada (`:8080`) la exploración interactiva de todos los microservicios sin exponer sus puertos internos ni requerir CORS.
  - Seguridad perimetral selectiva: se permite el acceso anónimo a la documentación OpenAPI y recursos estáticos de Swagger UI (`webjars`), mientras que los endpoints de negocio downstream continúan estrictamente custodiados por RBAC y validación JWT.

#### 2. ¿Qué hubo que arreglar sobre la marcha?
* **Compatibilidad de SpringDoc con Spring Boot 4.0.8 / Spring 7:** Se seleccionó la versión `3.0.2` de SpringDoc (`springdoc-openapi-starter-webmvc-ui` y `springdoc-openapi-starter-webflux-ui`), compatible de forma nativa con Spring Framework 7, Jakarta EE 11 y Netty reactivo.
* **Alineación de rutas OpenAPI y reescritura en Gateway:** La especificación de agregación requería consultar `/api/torneos/v3/api-docs` y `/api/partidos/v3/api-docs`. Dado que los microservicios downstream exponen sus contratos en `/v3/api-docs`, se configuró el filtro reactivo `rewritePath` en `GatewayRoutesConfig` para remover el prefijo de servicio downstream conservando el sub-path intacto.
* **Inicialización de contexto en tests de Gateway:** En las pruebas unitarias de `GatewayRoutesConfigTest`, `PathRoutePredicateFactory` requería la presencia de `WebFluxProperties` en el contenedor ligero de Spring. Se registró explícitamente dicho bean en el `GenericApplicationContext` de prueba, logrando ejecución 100% exitosa sin necesidad de levantar el servidor Netty completo.

#### 3. ¿En qué difiere con lo establecido en el Plan Original?
* **Enriquecimiento del Contrato Documental:** Se enriqueció `PartidoLoteController` con descripciones de esquemas para `ProblemDetail` (RFC 7807), permitiendo a los evaluadores visualizar en Swagger UI tanto los esquemas de éxito como los esquemas formales de error ante fallos de validación o autenticación.
* **No difiere en la arquitectura:** Se respetó estrictamente la división de responsabilidades fijada en `PLAN_DESARROLLO.md` para la Subsección 2.6 a cargo de Tomas Augusto Quiróz.

#### 4. Puntos Clave para la Defensa Oral (Coloquio con Docentes)
* **Agregación Perimetral de OpenAPI (Apunte 19):** Explicar cómo el API Gateway reactivo unifica múltiples especificaciones OpenAPI independientes en una única interfaz Swagger interactiva mediante `springdoc.swagger-ui.urls` y reescritura dinámica de rutas (`rewritePath`), evitando duplicación de código y desacoplando la documentación de cada microservicio.
* **Integración del Esquema de Seguridad Bearer JWT (Apuntes 20 y 21):** Explicar cómo el componente `@SecurityScheme(type = SecurityScheme.Type.HTTP, scheme = "bearer", bearerFormat = "JWT")` modela en OpenAPI el mecanismo de autenticación con Keycloak, permitiendo a los evaluadores autenticarse con el botón "Authorize" en Swagger UI y enviar la cabecera `Authorization: Bearer <token>` a los endpoints protegidos.
* **Estandarización de Respuestas de Error con RFC 7807 (Apunte 18):** Mostrar en Swagger UI cómo los endpoints documentan formalmente las respuestas de error 400, 401 y 403 con `application/problem+json`, demostrando coherencia integral entre la documentación OpenAPI y el manejador `@RestControllerAdvice` de `fulvo-common-lib`.
