#### 1. ¿Qué y Cómo se hizo?
* **Componentes / Módulos intervenidos:**
  - `servicio-torneos`: microservicio core de torneos donde se implementó la orquestación y el cliente REST fluido.
  - `servicio-notificaciones`: microservicio adaptador desacoplado de notificaciones por email hacia Mailpit (adelantando scaffolding y endpoint canónico de la Subsección 4.3 para habilitar la prueba integral E2E y el cumplimiento del criterio de aceptación 2.4).
  - `fulvo-common-lib`: integración del contrato común `NotificacionEmailDTO` con Bean Validation (heredado de `fix-validacionesDTOsLibreria`).
  - `postman`: creación de la suite de pruebas automatizadas `Fulvo - Subsección 2.4 - Notificaciones de Admisión.postman_collection.json`.

* **Archivos creados o modificados:**
  - `servicio-torneos/src/main/resources/application.yml`: configuración de `servicios.notificaciones.url` apuntando a `http://localhost:8083`.
  - `servicio-torneos/src/main/java/com/fulvo/torneos/config/RestClientConfig.java`: bean `RestClient` configurado con URL base de servicio-notificaciones.
  - `servicio-torneos/src/main/java/com/fulvo/torneos/config/AsyncConfig.java`: habilitación de ejecución asíncrona mediante `@EnableAsync`.
  - `servicio-torneos/src/main/java/com/fulvo/torneos/client/NotificacionesApiClient.java`: cliente `@Component` inyectado por constructor con `@RequiredArgsConstructor` invocando `POST /v1/notificaciones/emails` asíncronamente (`@Async`).
  - `servicio-torneos/src/main/java/com/fulvo/torneos/dto/PostulacionNotificacionRequest.java`: DTO de entrada para solicitud de postulación.
  - `servicio-torneos/src/main/java/com/fulvo/torneos/dto/AdmisionNotificacionRequest.java`: DTO de entrada para resolución de admisión (aprobada/rechazada con motivo).
  - `servicio-torneos/src/main/java/com/fulvo/torneos/service/TorneoNotificacionService.java`: servicio de dominio con métodos `despacharConfirmacionPostulacion` (FN-14) y `despacharResolucionAdmision` (RN-12, FN-05, RN-04) generando payloads HTML enriquecidos.
  - `servicio-torneos/src/main/java/com/fulvo/torneos/controller/TorneoNotificacionController.java`: controlador para invocar y probar el circuito de notificaciones.
  - `servicio-notificaciones/pom.xml`: proyecto Spring Boot 4.0.8 / Java 21 independiente con starters web, mail, validation, actuator y `fulvo-common-lib`.
  - `servicio-notificaciones/src/main/resources/application.yml`: puerto 8083 y conexión SMTP a `mailpit:1025`.
  - `servicio-notificaciones/src/main/java/com/fulvo/notificaciones/ServicioNotificacionesApplication.java`: clase principal de Spring Boot.
  - `servicio-notificaciones/src/main/java/com/fulvo/notificaciones/service/EmailSenderService.java`: servicio que compone mensajes MIME HTML y aplica captura silenciosa de excepciones SMTP.
  - `servicio-notificaciones/src/main/java/com/fulvo/notificaciones/controller/NotificacionEmailController.java`: controlador `POST /v1/notificaciones/emails` respondiendo HTTP 202 Accepted.
  - `postman/Fulvo - Subsección 2.4 - Notificaciones de Admisión.postman_collection.json`: colección con 7 pruebas automatizadas (`pm.test`).

* **Endpoints y Contratos implementados:**
  - `POST /v1/torneos/notificaciones/postulacion`: recibe `PostulacionNotificacionRequest`, responde HTTP 202 Accepted y dispara asíncronamente el email de postulación recibida (FN-14).
  - `POST /v1/torneos/notificaciones/admision`: recibe `AdmisionNotificacionRequest`, responde HTTP 202 Accepted y dispara asíncronamente el email de aprobación o rechazo con motivo (RN-12).
  - `POST /v1/notificaciones/emails`: endpoint canónico del adaptador en puerto 8083 que recibe `NotificacionEmailDTO`, lo valida con Bean Validation y lo despacha a Mailpit.

* **Lógica técnica y de dominio aplicada:**
  - Se utilizó `RestClient` fluido (Spring 6 / Boot 3) prohibiendo expresamente `RestTemplate`.
  - Toda la inyección de dependencias se realizó mediante atributos `private final` y `@RequiredArgsConstructor` de Lombok.
  - El despacho desde `servicio-torneos` es no bloqueante (`@Async`), garantizando que la latencia o indisponibilidad del servicio de correos no penalice el tiempo de respuesta del usuario.
  - En `servicio-notificaciones`, el `EmailSenderService` implementa captura silenciosa ante fallos de conexión SMTP (Mailpit caído), registrando el error en el log pero sin romper la transacción ni propagar un 500 al cliente llamador (resiliencia operativa RN-12).

#### 2. ¿Qué hubo que arreglar sobre la marcha?
* **Problemas técnicos encontrados:**
  - En la rama `fix-validacionesDTOsLibreria`, Luis Miguel había agregado validaciones estrictas (`@NotBlank`, `@Email`, regex de tipo de evento) y el manejador RFC 7807 para `HandlerMethodValidationException`. Dicha rama no había sido integrada a `subseccion2.4`.
  - La Subsección 2.4 exigía como criterio de aceptación que los correos llegaran a Mailpit (`:8025`), pero el microservicio `servicio-notificaciones` estaba planificado originalmente para la Subsección 4.3 (ambas a cargo de Luis Miguel). Sin `servicio-notificaciones`, cualquier invocación de `RestClient` fallaba por conexión rechazada y ningún email llegaba a Mailpit.
* **Soluciones y Workarounds aplicados:**
  - Se realizó fast-forward merge de `fix-validacionesDTOsLibreria` en `subseccion2.4` y se recompiló/instaló `fulvo-common-lib` en el repositorio `.m2` local con `mvn clean install -DskipTests`.
  - Se adelantó el scaffolding liviano y la lógica de `servicio-notificaciones` (puerto 8083, Spring Mail, Mailpit 1025) para que `servicio-torneos` pueda interactuar de punta a punta y certificar el Criterio de Aceptación 2.4 de forma real.

#### 3. ¿En qué difiere con lo establecido en el Plan Original?
* **Modificaciones del Modelo de Datos / Entidades:** Ninguna modificación; los esquemas de bases de datos se mantienen inalterados.
* **Ajustes en Funcionalidades o Reglas:** Se creó un controlador dedicado `TorneoNotificacionController` en `servicio-torneos` para poder despachar y validar de forma inmediata e independiente las notificaciones de postulación y admisión mientras Gastón completa las entidades y endpoints CRUD de las Subsecciones 2.1 y 2.2. Cuando Gastón implemente `SolicitudInscripcionService`, solo deberá inyectar `TorneoNotificacionService` y llamar a sus métodos.
* **Motivo del cambio:** Permitir desarrollo concurrente desacoplado entre los miembros del equipo y certificar el 100% del Criterio de Aceptación 2.4 sin bloquearse por tareas ajenas.

#### 4. Puntos Clave para la Defensa Oral (Coloquio con Docentes)
* **Decisiones de diseño a defender:**
  - **Uso de `RestClient` vs `RestTemplate`:** Se utilizó la API moderna fluida de Spring Boot 3 / Spring 6, permitiendo un código declarativo, sincrónico o asíncrono, fuertemente tipado e inyectado limpiamente como Bean.
  - **Asincronía y Desacoplamiento:** El envío de notificaciones es una tarea secundaria respecto al registro de la postulación o la admisión; por ende, debe ser no bloqueante (`@Async`) y tolerante a fallos (captura de excepción SMTP en el adaptador).
  - **Resiliencia Operativa (RN-12):** Si el servidor de correos (Mailpit) está caído o sobrecargado, la postulación o admisión del equipo no debe cancelarse ni arrojarse un error 500 al usuario.
  - **Trazabilidad MDC:** Toda petición HTTP propaga el `X-Correlation-ID` tanto en `servicio-torneos` como en `servicio-notificaciones`.
* **Preguntas probables de los profesores:**
  - *¿Por qué el envío de correo no forma parte de la transacción de base de datos?* Porque las operaciones de red externas (SMTP/HTTP) introducen latencias impredecibles y pueden bloquear conexiones de pool de base de datos; además, una falla de SMTP no debe deshacer una inscripción válida.
  - *¿Cómo se evita que un fallo en el microservicio de correos afecte a torneos?* Mediante la ejecución asíncrona (`@Async`) y el bloque `try-catch` con log en el cliente y en el adaptador, respetando el principio de aislamiento de fallos.
