* **Lógica técnica y de dominio aplicada:**
  - Red perimetral `bda-net`: Los 5 microservicios de backend y adaptadores no publican puertos en las interfaces de red de la máquina host (`ports` omitido, uso estricto de `expose`), impidiendo el bypass perimetral de seguridad. Toda comunicación entrante externa o de clientes debe atravesar forzosamente el `api-gateway` en el puerto `8080`, donde se aplican los filtros de Spring Cloud Gateway, validación JWT de Keycloak y encabezados de correlación.
  - Enlaces de nombres DNS internos: La resolución inter-servicio utiliza los nombres canónicos de contenedor dentro de la red Docker (`postgres-db:5432`, `keycloak-server:8090`, `mailpit:1025`, `wiremock:8080`, `servicio-torneos:8081`, `servicio-operaciones-partidos:8082`, etc.).

#### 2. ¿Qué hubo que arreglar sobre la marcha?
* **Colisión de puerto 8080 en el host durante el arranque:**
  - *Problema:* Al ejecutar `docker compose up -d --build`, el contenedor `api-gateway` falló al intentar vincular el puerto `0.0.0.0:8080` debido a un proceso Java previo en el host que no se había cerrado tras los tests de la Etapa 4.
  - *Solución:* Se inspeccionó el puerto mediante `netstat -ano`, se identificaron y detuvieron los procesos Java residuales del host, y se relanzó `docker compose up -d`, iniciando `api-gateway` en estado `healthy`.
* **URLs cableadas en archivos de configuración:**
  - *Problema:* `servicio-geocodificacion` y `servicio-clima` tenían configuradas las URLs de Nominatim y Open-Meteo directamente a `localhost:8086`, lo que impedía que en Docker se redirigieran al contenedor `wiremock:8080`.
  - *Solución:* Se parametrizaron con variables de entorno `${NOMINATIM_BASE_URL:http://localhost:8086}` y `${OPEN_METEO_BASE_URL:http://localhost:8086}`, e inyectadas en `docker-compose.yml` apuntando a `http://wiremock:8080`.

#### 4. Puntos Clave para la Defensa Oral (Coloquio con Docentes)
* **Decisiones de diseño a defender:**
  - *Aislamiento perimetral con `expose` vs `ports`:* La directiva `expose` solo documenta e intercomunica puertos entre contenedores dentro de la misma red Docker (`bda-net`), sin abrir sockets en la interfaz del host. Esto garantiza el principio de mínima superficie de ataque (Zero Trust Perimetral) exigido por la cátedra.
  - *Imágenes optimizadas JRE Alpine:* Se utilizó `eclipse-temurin:21-jre-alpine` (solo el runtime de ejecución Java sin compiladores ni herramientas innecesarias de SDK), reduciendo drásticamente el peso de las imágenes y la superficie de vulnerabilidades de seguridad.
  - *Healthchecks nativos y arranque ordenado:* Cada contenedor cuenta con un healthcheck HTTP (`/health-check`) con `start_period: 30s` para permitir el inicio de Spring Boot y `retries: 5`, coordinando las dependencias inter-servicio mediante `depends_on`.
* **Preguntas probables de los profesores:**
  - *¿Por qué un cliente no puede consultar directamente `http://localhost:8081/v1/torneos`?* Porque el microservicio `servicio-torneos` no tiene mapeo de puertos hacia el host. Toda petición debe ingresar por `http://localhost:8080/v1/torneos` pasando por el API Gateway, lo cual garantiza autenticación OIDC centralizada, auditoría y correlación.
